# Модель безопасности

Эта страница объясняет, от каких типичных проблем при работе с архивами защищает Archive Guard,
какие проверки выполняет пакет и какие риски приложение всё равно должно контролировать само.

Это описание поведения библиотеки, а не отчёт о формальном аудите безопасности.

## Какие данные архива считаются потенциально опасными

Archive Guard не доверяет данным, которые пришли из самого архива. В частности, проверяются:

- имена и пути файлов;
- типы записей: обычный файл, каталог, ссылка или специальный объект;
- заявленные размеры файлов;
- общий объём распакованных данных;
- сведения о сжатии;
- дополнительные возможности ZIP, TAR и TAR.GZ.

Причина простая: архив может быть корректным как файл, но содержать путь вроде `../file`,
символическую ссылку, огромный распакованный файл или возможность формата, которую приложение
не ожидает обрабатывать.

## Что делает `inspect()`

[`ArchiveGuard::inspect()`](../src/ArchiveGuard.php) проверяет архив без извлечения файлов.

Проверка включает:

- нормализацию и проверку путей;
- поиск конфликтующих путей;
- проверку типов записей;
- ограничения из [`ArchivePolicy`](../src/ArchivePolicy.php);
- проверки, специфичные для ZIP, TAR и TAR.GZ.

Если архив корректный, но нарушает одно из правил, приложение получает
[`InspectionResult`](../src/InspectionResult.php) со списком причин. Если сам файл нельзя
надёжно прочитать или разобрать, возникает `ArchiveOpenException`.

## Что делает `extract()` перед записью

[`ArchiveGuard::extract()`](../src/ArchiveGuard.php) не доверяет результату старого вызова
`inspect()`. Перед извлечением архив проверяется заново.

После этого пакет:

1. убеждается, что каталог назначения уже существует и пуст;
2. проверяет, что сам каталог назначения не является символической ссылкой;
3. не перезаписывает существующие файлы;
4. контролирует фактическое количество записанных байтов;
5. для TAR и TAR.GZ повторно сверяет записи при втором проходе с теми, которые были приняты
   при первой проверке.

Каталог создаёт приложение, а не библиотека. Это намеренное разделение ответственности:
приложение выбирает место распаковки и права доступа, а Archive Guard работает только
внутри уже подготовленного пустого каталога.

## Ограничение потребления ресурсов

Четыре обязательных предела ограничивают:

- размер исходного файла архива;
- количество записей внутри архива;
- размер одной записи после распаковки;
- общий объём распакованных данных.

Необязательный `maxCompressionRatio` добавляет ещё одну проверку против слишком сильного
расширения сжатых данных:

- для ZIP используются размеры из метаданных;
- для TAR.GZ учитывается фактический объём данных от декомпрессора;
- для обычного TAR этот предел не применяется.

Это дополнительная эвристика, а не замена основным ограничениям размера.

## Особенности Windows

Некоторые имена допустимы внутри ZIP или TAR, но не могут быть безопасно созданы в Windows.

Перед записью пакет дополнительно отклоняет, например:

- зарезервированные имена устройств `CON`, `NUL`, `PRN` и подобные;
- недопустимые символы Windows;
- имена с точкой или пробелом в конце;
- пути, различающиеся только ASCII-регистром, если Windows будет считать их одним путём.

Поэтому общий `inspect()` может принять такой архив, а `extract()` на Windows остановится
до первой записи с `ExtractionException`.

## Ограничения и почему они существуют

### Извлечение не атомарно

Archive Guard пишет файлы непосредственно в подготовленный каталог. Если операция оборвётся
после нескольких успешно записанных файлов, они останутся на диске.

Полностью атомарная схема потребовала бы сначала распаковать всё во временный каталог,
а затем одним финальным действием заменить или перенести весь результат. Такое перемещение
имеет разные ограничения на разных файловых системах и в Windows и потребовало бы отдельного
публичного контракта. Текущая версия поэтому явно не обещает атомарность.

### Пакет не может заблокировать файловую систему от других процессов

Во время работы Archive Guard проверяет каталог и создаваемые пути, но PHP-библиотека не
может запретить другому процессу одновременно изменить тот же каталог.

Это не означает, что обычное извлечение «небезопасно». Ограничение относится к среде,
где недоверенный процесс уже имеет возможность параллельно менять каталог назначения.
Для такого сценария приложение должно использовать отдельный закрытый каталог и подходящие
права доступа на уровне операционной системы.

### Права и владелец из архива не восстанавливаются

Архив может содержать собственные права доступа, владельца и временные метки. Archive Guard
их намеренно не применяет: извлечённые файлы создаются с обычными настройками PHP-процесса
и операционной системы.

Так архив не может сам назначить извлечённым файлам неожиданные права или владельца.

### Не каждая возможность ZIP или TAR поддерживается

Если Archive Guard не понимает возможность формата достаточно надёжно, он отклоняет архив,
а не пытается угадать правильное поведение. Например, текущая версия не извлекает
зашифрованные ZIP-записи.

Точный список ограничений приведён в
[справочнике поддерживаемых архивов](reference/supported-archives.md).

## Практические рекомендации

- задавайте лимиты `ArchivePolicy` под реальные размеры архивов вашего приложения;
- используйте отдельный пустой каталог для каждой операции извлечения;
- не давайте недоверенным процессам возможность одновременно менять этот каталог;
- отдельно обрабатывайте нарушения проверки, ошибки открытия и ошибки записи;
- если приложение само создало временный каталог и полностью им владеет, после неудачного
  извлечения оно может удалить его по своим правилам.
